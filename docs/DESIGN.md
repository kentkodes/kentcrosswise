# Kentcrosswise: Design

Current architecture and accepted decisions, consolidated 2026-10-25; section 4.0 records the owner-accepted direction of 2026-11-14, and section 4.6 the owner direction of 2026-11-17 (personal helper, public log). Implements the approved [hub](hub/SPEC.md) and [essays](essays/SPEC.md) specs. [HANDOFF.md](HANDOFF.md) records observed source/deployment status; [OPEN-POINTS.md](OPEN-POINTS.md) is the active backlog. Vendor research is dated evidence, not a fresh validation. Accepted targets and task tables are delivery contracts, not claims that implementation or live acceptance has passed.

## 0. Accepted architecture decisions

| D1 | pnpm workspaces; extra top-level `packages/` for shared libs (`core`, `db`, `secrets`, `essays`, `demo-data`, `xray`) | Fewest moving parts; `pnpm -r` is enough at this size. |

Components:
- **Web** (`apps/web`): one Next.js 16 App Router app on Lambda via OpenNext v4. Route groups: `(public)` (demo, X-ray, office, `/terms`, `/privacy`) and `(owner)` (hub, boss console, inbox). `/essays` is mounted from `@kcw/essays`. Auth.js with Google, allowlisted owner email. The essay reader loads full text with `s3:GetObject` on `essays/text/*` in the private pipelines bucket (prod only; bucket name in env `ESSAY_TEXT_BUCKET`; previews have no bucket and show "Text unavailable").
- **Orchestrator** (`agents/orchestrator`): Lambda with an SQS FIFO trigger, batch size 1. Each invocation loads the task's LangGraph thread from the Neon checkpointer, runs to the next `interrupt`, and returns. Target under 2 min per invocation; timeout 5 min. LangSmith env: `LANGSMITH_TRACING=true`, `LANGCHAIN_CALLBACKS_BACKGROUND=false` (flush before freeze).
- **Webhook relay** (`agents/webhook-relay`): Lambda Function URL. It verifies `X-Hub-Signature-256`, dedupes by `X-GitHub-Delivery`, drops events whose sender is not one of our Apps or the owner, normalizes them and enqueues to `orchestrator-in`.
- **Agent workflows** (`.github/workflows/agent-*.yml`): Claude Code Action with the agent's playbook. Developer, Scraper-builder and Docs-keeper run `deepseek-flash` through `https://api.deepseek.com/anthropic`; their work jobs read one secret, `kcw/agent/deepseek`, through the GitHub environment `agent-model` (main only) and role `kcw-gh-agent-model`, which can read only that secret; the key is masked, and the job has no App identity or publisher access. QA work and QA review run `claude-haiku-5-5` through Anthropic workload identity federation (GitHub OIDC; no key, no `agent-model` environment, no AWS role). Publishers authenticate to GitHub as their own App and report events and usage by sending messages to `orchestrator-in`.
- **CI/deploy workflows**: `ci.yml` (per PR), `deploy.yml` (push to main), `preview-gc.yml` (PR closed + nightly dispatch by the sweeper; no GitHub `schedule`, because public repos disable schedules after 60 inactive days).
- **Pipelines** (`pipelines/`): watcher Lambda (EventBridge) and a runner Lambda (SQS `essay-urls`) that chains extract, validate and categorize. All plain code except the categorizer call.
- **Scheduler**: EventBridge schedules for the orchestrator sweeper (15 min), nightly source health + preview GC dispatch, weekly quality report, and the watcher. Web-side jobs: EventBridge Scheduler invokes the prod server Lambda directly (`kcw-prod-hub-jobs-scheduler` role, one schedule per job in `infra/modules/web/jobs.tf`, UTC, flexible window off) with `{"kcw_job": "<name>", "scheduled_time": "..."}`. The `kcw-origin-guard` wrapper routes a non-HTTP payload (plain object, no `requestContext`, `headers` or `rawPath`, string `kcw_job`) to the fixed registry in `apps/web/src/server/jobs/` before the origin check; every HTTP request still goes through the D25 check. A job returns `{job, code, counts}`, never data; failure logs `[job] <name> failed <ErrorClass>` and rethrows. Prod schedule: `inbox-push` `cron(0/15 * * * ? *)`. Async invokes have zero Lambda retries (`aws_lambda_function_event_invoke_config`); the schedule's own retry policy allows up to two retries within one hour.
- **Model providers** (`packages/core/models`): `classify(input, labels) -> {label, confidence, model}` and `complete/score`. Implementations:
  - `DeepseekProvider`: OpenAI-compatible Chat Completions over `fetch` (no SDK). Model defaults to the alias `deepseek-flash` and base URL to `https://api.deepseek.com` (first-party API); the optional secret keys `deepseek_model` and `deepseek_base_url` override them (e.g. a gateway with the dated id `deepseek/deepseek-v4.1-flash-1017`), so changing model or endpoint needs no code change. `classify` forces a function call returning `{label, confidence}` and falls back to a JSON object in the message; a label outside the labels is a non-retryable `ProviderError`. 429, 5xx and network errors are retried with backoff.
  - `AnthropicProvider`: the orchestrator planner passes `claude-opus-5-5` with `effort: high` (sent as `output_config.effort`); the default for other callers stays `claude-haiku-5-5` (prompts under 100K tokens, price cliff above that).
  - `FakeProvider`.
  - `withFallback(threshold)` (not used at runtime now): Haiku when the primary's confidence is below the threshold or the primary returns an error (429/529 retried with backoff first).
  - Every call writes a `usage_events` row.

## 3. Data model (Postgres, Neon)

Schemas: `public` (app) and `lg` (LangGraph checkpointer tables, with runtime ownership verified; real-task persistence/resume remains a live acceptance gap). All timestamps are `timestamptz`. Only synthetic seed data lives in `packages/db/seeds`.

|---|---|
| `entries` | id, created_at, source (`web`,`shortcut`), raw_text, route_kind (`crm_note`,`diary`,`todo`,`idea`,`agent_request`, null=pending), route_confidence, route_model, routed_by (`model`,`owner`), status (`routed`,`needs_owner`), time_zone (IANA zone of the capture, null for older rows; 1-64 characters), route_error (null, or `provider_error`, `invalid_label`, `spend_cap`: the fixed code of the last failed routing attempt, never a message or text), route_attempts (integer, default 0), route_attempted_at (migration 0014) |

| `projects` | slug, title, sort |

| `push_subscriptions` | id, endpoint UNIQUE, keys jsonb, created_at |

Derived rows. `crm_notes`, `diary_entries`, `todos` and `ideas` each have a partial unique index on `entry_id WHERE entry_id IS NOT NULL` (migration 0014): one derived row per entry and kind, and writes use ON CONFLICT DO NOTHING. `applyRoute` in `apps/web/src/server/derived.ts` creates the row in the same transaction that sets the route. Reassignment moves the current body of the old row to a new row of the new kind. A same-kind save changes nothing, so a derived row the owner deleted stays deleted. Moving to `agent_request` discards the old derived row, including edits to its body, because agent requests have no destination table until their approval flow exists (after MVP); `entries.raw_text` never changes.

Contacts (H4). Owner pages `/contacts`, `/contacts/new` and `/contacts/[id]` (Dense UI), code in `apps/web/src/server/contacts.ts`; no migration (tables from 0001). `linkCrmNote(db, noteId)` matches contact names and aliases in a note as whole words, case-insensitive, with Unicode letters, digits and underscore as word characters. Names and notes are compared in NFC, and whitespace inside a name matches any whitespace run. One match links the note; several set `link_status` to `ambiguous` and open one `inbox_items` row (kind `contact_match`, ref `crm_notes`); none sets `none`. Creating a contact, or changing its name or aliases, re-runs the match, in the same transaction, for the newest 500 notes whose `link_status` is `none`; linked and ambiguous notes are not touched. The owner's choice (`resolveCrmNote`) sets the link and closes the item. Deleting a contact sets its notes' `link_status` to `none`. `orch_rw` still reads contact names and aliases for the sanitizer. There is no last-contact tracking or reminder. `applyRoute` does not call `linkCrmNote` yet, and `ContactMatchRegion` is not yet shown on `/inbox` (H12).

Mood. `/diary`, `/diary/[id]` and `/mood` use `diary_entries` and `mood_scores`; scoring is in section 9. Social was removed on 2026-11-17; migration 0024 dropped `social_accounts` and `social_snapshots`.

Routing links and derived follow-ups (wave 2). A route's CRM note is linked to a contact in the route transaction: `applyRouteLinked` in `apps/web/src/server/router.ts` runs `linkCrmNote` in a savepoint, so a failed link keeps the route and leaves the note unlinked; an ambiguous match shows "Choose a contact" and adds a `contact_match` inbox item. After the transaction commits, `scoreCreated` in `apps/web/src/app/(owner)/routing.ts` scores a created diary row, bounded to 6 s; a timeout or failure leaves it "Not scored" with "Score again" on the diary page. The model is never called inside a transaction. A created CRM note gets one calendar suggestion after commit (`suggestFromNote` in `apps/web/src/server/calendar.ts`, 6 s bound, also after owner reassignment in `routing.ts`): the router's DeepSeek provider looks for a dated plan in the entry's time zone (`entries.time_zone`; without a zone there is no suggestion). A valid reply stores one suggestion per note (unique on `crm_note_id`) and a `calendar` inbox item. Adding it posts to the primary calendar with the suggestion's UUID (no dashes) as the event id, so a repeated tap is safe; HTTP 409 counts as added and 401 keeps it pending. The Google calls have an 8 s timeout.

Google connection (W2-3). `/connections` is the owner page. `events.signIn` in `apps/web/src/auth/config.ts` writes the refresh token to `kcw/prod/google-owner-token` only when the consent grants `calendar.events.owned`; `apps/web/src/server/google.ts` reads it (`googleAccessToken`, `googleConnection`) and clears it on `invalid_grant` or disconnect (`disconnectGoogle`, which revokes at Google). Calendar is the only API scope requested.


Web push (W2-6). The `inbox-push` job (every 15 minutes) sends one generic notification (title `Kentcrosswise`, body `N new items in your inbox`, url `/inbox`) to each row of `push_subscriptions` when open inbox items have no `notified_at`, then sets `notified_at` on the items it announced. The payload never carries item text. Encryption is RFC 8291 (aes128gcm) and authentication RFC 8292 (VAPID, ES256, `sub` = `https://kentcrosswise.com`), both with `node:crypto` (`apps/web/src/server/push/{ece,vapid,send}.ts`). Endpoints are posted to only on an allowlist of push-service hosts. A 404 or 410 deletes that subscription. The VAPID keys are `vapid_public` and `vapid_private` in the web secret; without them the job returns `off`. `/notifications` enables, disables and tests a device; `apps/web/src/app/manifest.ts` and `apps/web/public/sw.js` make the site installable. iPhone delivers push only to a Home Screen web app (iOS 16.4 or later).

### 4.2 PR loop (one subtask)
1. The owner creates a task in the boss console. This writes a `tasks` row and sends the SQS message `{type: task.created}`.
2. Orchestrator:
   - Checks `agents_paused` and the two limits of D20. **Admitted work** (`IN_FLIGHT_LIMIT` = 4): tasks in `planning`, `in_progress` or `waiting`, claimed by `claimSlot` at start. **Active execution** (`ACTIVE_EXECUTION_LIMIT` = 1 for rollout, owner decision 2026-11-17, raised after AR9; AR6): tasks that wait on a Developer, QA or Docs run, that is `status = 'waiting' AND waiting_on IN ('dev','qa')`. A task holds this reservation from the moment `claimExecution` succeeds (before the dispatch intent) until its next `enter(phase)` writes another `waiting_on` (`ci`, `owner`, null at the end); parked owner, CI and merge waits hold none. There is no reservation table. `claimExecution` uses the same transaction and advisory lock as `claimSlot`; a holder keeps its reservation (a redispatch or a re-run step claims nothing twice); parents with children and unadmitted (`queued`, terminal) tasks are not granted or counted. At the limit it sets `tasks.execution_wait` to the role and the dispatch is refused: the machine stores `pending_capacity`, logs `execution_full role=<role>` (no text) and returns outcome `queued`. Every sweep, in any phase, retries a pending capacity dispatch before anything else; there is no wake-up message and no queue order beyond the sweep's id order. A task refused at its first Developer dispatch keeps status `planning` and is retried by the stale-planning sweep (15 minutes), not the next sweep: slower, not stuck. A dispatch GitHub refuses (a 4xx other than 408 and 429: no run exists) puts the task row back to what its phase says, so its reservation is released; the step still fails and its re-run claims again. Both limits are 4, so the active limit does not bind yet; the rollout value is the owner's decision (the plan recommends 1; changing it is one line in `graph/types.ts`).
   - Plans 1-5 nonrecursive subtasks under Q12; one subtask uses the task itself, multiple subtasks receive child rows. Ordering (AR4, migration 0020): each subtask is a string (it waits for the subtask before it) or `{"text", "after": [1-based numbers]}`; `"after": []` marks it independent. A self reference, an unknown subtask, a repeated entry or a cycle is invalid planner output (retried once, then the owner failure of Q12(6)). Each child row stores its prerequisites as sibling ids (`tasks.prerequisites`). The split writes the children and, in the same transaction, an `orchestrator_outbox` row `{type: task.created, task_id, message_key: task-<child>/start}` for every child without prerequisites; the parent's invocation makes no child model call. A child's merge, in the same transaction as its `merged` status, records `tasks.merge_sha` on that child (the merge commit GitHub returned; none for a merge seen only by webhook; a value already recorded is kept) and enqueues the start message of every queued sibling whose prerequisites are now all merged. A consumer starts only after all its prerequisites are merged, so `main` at its dispatch contains them. A start or sweep of a child whose prerequisites have not all merged leaves it `queued`. The child's issue footer lists its prerequisites' merge commits (the line "Prerequisites merged on `main`: <sha>, <sha>.", in prerequisite order). Nothing pins the dispatch base; the worker's contract check (section 4.1) verifies that the base and each prerequisite merge are contained in `main`.
   - Writes the public title and runs the sanitizer (4.5). The planner plans with a repository brief: the `## Layout` section of `docs/agents/INSTRUCTIONS.md` (at most 8,192 bytes), read through the contents API at the base commit, which is the head of `main` read at planning (`getBranchHead("main")`). Both nodes get it in a `<repository>` block before the `<task>` block, and the whole prompt is bounded by 40,960 bytes. A missing, empty or oversized section, or a prompt over the bound, goes to the owner as a planning failure with fixed text; no model call is made. The public-title node answers `{title, body, acceptance, scope, context}`: `acceptance` has 1 to 10 items of at most 400 characters, `scope` and `context` 0 to 20 repository paths each (the `@kcw/core/contract` path rule). The `plan` operation record stores the base, the brief, the prerequisites (`{task, merge}` from each prerequisite's `tasks.merge_sha`; one without a recorded merge commit goes to the owner) and the plan, so a re-run makes no second `getBranchHead`, `readFile` or model call. After the issue is published the orchestrator builds the task contract (version 1, revision 1: `issue` = the published issue, `goal` = the sanitized issue body, `acceptance`, `scope`, `context`, `base`, `prerequisites`) and keeps it in the checkpoint (`contract`). Every Developer and QA dispatch of a work task carries it as the `contract` input (canonical JSON), so the dispatch operation's request hash covers it; QA gets the contract the Developer got. A work task that reaches such a dispatch without a contract (planned before this slice) fails with a fixed reason and is not sent to the owner or planned again; planning again with a new revision is AR5b. Docs-keeper dispatches and the QA dispatch for a docs task carry no contract. Owner text and subtask text never enter the contract.
   - Creates the GitHub issue with sanitized text only. If the sanitizer fails, it creates `approvals(kind=issue_text)` and interrupts with `wait=owner`.
   - Dispatches `agent-developer.yml`, records event `task_assigned`, then `interrupt(wait=dev)`.
   - The planner answers, the issue, every dispatch and the merge go through operation records (section 4.3, "Operation records"); a re-run of the step reconciles instead of repeating the effect.
3. The Developer workflow opens PR `kcw/task-<id>`. Webhook `pull_request.opened` → relay → resume. Events `pr_opened` and `ci_running`, then `interrupt(wait=ci)`.
4. `ci.yml` (same-repo PRs only):
   - lint + unit + build;
   - credential-free `candidate-build` (migrate + seed on a service database, preview build, uploaded as data);
   - prod `terraform plan` with the read-only role;
   - summary artifact for merge-rules;
   - `ci/required` check.
   `preview-trusted.yml` (`workflow_run`, section 5) provisions the preview, runs Playwright and tears it down.
5. `workflow_run.completed` → resume.
   - Failed: event `tests_failed`. If attempts < 3, dispatch the Developer with `mode=fix` and go back to step 3; otherwise send an approval to the owner (`failed`). AR5b: for a task with its issue and contract the approval uses `retry: "plan"` with the text "Approve to replan the task (new contract revision; the PR is kept, CI is reused for an unchanged head, QA reviews again); reject to mark it failed." Approving runs `bumpOp("plan")` and the public-title node only (never `split`) with the previous contract and the fixed line `Revision r used N of 3 attempts without an approved QA review.`; the new contract keeps issue, base and prerequisites, takes revision r+1 and is sanitized as revision 1 (the issue is not edited). The planner prompt carries a `<previous_contract>` block and a `<failure>` block between `<repository>` and `<task>`; a first plan and `split` never get them. Then the old revision's attempts and QA evidence are superseded, `attempts = 0`, and: no PR, Developer `implement`; CI success at the head, QA; CI failure at the head, Developer `fix`; CI unknown, wait for CI. A task without a contract (planned before AR5a) keeps the Developer retry ("give the Developer 3 more attempts"); approving dispatches the Developer, whose dispatch fails the task ("the task was planned before task contracts existed; create the task again"). An approved fresh-plan retry also fails a task that has a PR instead of planning it again. Timeouts keep their retry targets.
   - Passed: dispatch QA, then `interrupt(wait=qa)`.
6. QA may publish tests. A new head returns through CI and then a fresh independent source-only QA review; approval binds that exact head and successful ci/required. QA submits its review. `pull_request_review.submitted` → resume. Changes requested → Developer `fix` (counts toward attempts). Approved → step 7. Evidence validity (AR5b, `graph/validity.ts` `evidenceValid`): a report whose `contract` differs from the current revision's hash is obsolete (usage recorded, event not). A QA review, approval or changes request, counts only if its revision is current and not superseded, its head is the current head, and it comes from the revision's latest QA attempt once that attempt has `started_at` (set by its start report); otherwise it is logged `review_not_valid`, nothing is recorded and no attempt is counted. CI success is valid for any revision while its head is the PR head: a non-superseded `success` row for the head, where the latest CI result of the head comes from the checkpoint (`d.ci`), which the merge step and the replan check first; a replan reuses CI only when the checkpoint's CI result is for the current head. A docs task has no revision condition. The merge step re-checks CI and QA evidence for the head before merging, backfills CI evidence from `d.ci` for older checkpoints (never QA evidence), and dispatches QA again for the current revision when the QA evidence is invalid (no owner step). Reports and approvals from before 0021 have no attempt row: a report without a row records usage and applies its event as before, and an approval then has no started QA attempt, so the merge step dispatches QA again. Known residuals: a review is bound to the revision's latest started QA attempt and the head, not to the run that posted it, so a delayed review of revision r that arrives after revision r+1's QA attempt started, at the same head, is counted; an approval that arrives before its QA attempt's start report is not applied and not re-checked later (the QA timeout redispatches QA once).
7. Merge-rules runs on the latest head SHA (diff + plan summary).
   - Critical: `kcw/merge-rules` stays pending; create `approvals(kind=critical_pr, reasons)`; inbox item + push notification; event `waiting_on_owner`; `interrupt(wait=owner)`.
   - Not critical, or owner approved: check success → squash merge → event `merged`.
8. Push to main → `deploy.yml` (environment `prod`): prod web build and Lambda bundles first (no AWS credentials, so a failed build leaves the production schema and infrastructure untouched), then migrate, `terraform apply infra/prod` (uploads the OpenNext build and Lambda code), invalidate CloudFront `/*` and wait, then smoke-check that public pages show this build id. Merged, deployed and verified are three separate facts bound to the commit and build id ([runbooks/release-recovery.md](runbooks/release-recovery.md)); the sweeper part `releases` records them per merge commit (section 4.3). Reporting `deployed` as an event is separate future work (the event type stays defined but unused).
   - Docs-keeper is dispatched at merge, not after deploy: in the step that squash-merges a task PR, the orchestrator creates the docs task (a child row of the merged task, §3.2), and the handler starts its thread. Only PRs the orchestrator merges trigger it; owner/local merges and docs PRs do not.
   - The docs task takes an in-flight slot (D20) and waits `queued` like any task when paused or at the limit. Its start skips the planner, the public-title node and the issue: it dispatches `agent-docs.yml` {task_id = the docs task, pr = the merged PR} (run-name `docs task <task_id>`), records `task_assigned` (agent `docs`) and waits on `dev`.
   - Its PR (branch `kcw/task-<docs task>`) goes through steps 3-7 unchanged, including merge-rules and the owner's critical gate (`docs/agents/**` and root adapters are critical). There is no Developer: a CI failure, QA changes requested or a refused merge (for example conflicting docs PRs) goes to the owner as a failure; approving re-dispatches Docs-keeper, rejecting marks the docs task `failed`.
   - A run that changes nothing opens no PR; the sweep (§4.3) then ends the docs task `done` with no event or inbox item.
   - The parent task is `done` when all children are merged (docs tasks are children of the merged subtask, not of the parent, so they never hold it up). A failed or cancelled child blocks the queued children that depend on it, directly or not: they never start. Once no other child can make progress, the parent's sweep parks it for the owner (`critical_pr` approval naming the ended child and the blocked ones); either decision cancels the blocked children and marks the parent `failed` (replanning the rest is AR5b).

Owner status (AR6): the boss console shows one capacity line above the task list, "Active workers N · Admitted work M (parked: owner a, CI b, waiting for a worker c) · Queued q". Definitions, all over `tasks` rows without children: active = `status = 'waiting' AND waiting_on IN ('dev','qa')`; admitted = `status IN ('planning','in_progress','waiting')`; parked = admitted minus active, split in this order into owner (`waiting_on = 'owner'`), CI (`waiting_on = 'ci'`), waiting for a worker (`execution_wait` set) and other (planning, or waiting with neither); queued = `status = 'queued'`. A task waiting on the owner with `execution_wait` set counts as owner. Rows with `execution_wait` set show "Waiting for a worker". The line shows counts only (the "other" count is computed but not shown); limits are not shown. Below it the "Releases" block lists the last 10 rows of `task_releases` (section 4.3).

### 4.3 Resuming from interrupts
- **Threads:** each task is one LangGraph thread (`thread_id = task-<id>`), checkpointed in Neon (`lg` schema). Fresh-instance persistence/resume is source-tested; real-task runtime acceptance remains open.
- **Routing events to a thread:** the relay and workflow reports resolve the task from `branch`, `pr_number` or the `task_id` input. They enqueue `{thread_id, resume: {event, head_sha, payload}}` with `MessageGroupId = thread_id` and `MessageDeduplicationId = delivery id`.
- **Delivery path (AR2 slice 1, migration 0011):** an accepted orchestrator input is committed to `orchestrator_outbox` (key = the logical message identity) together with its claim or mutation, then sent, then marked sent. The relay does claim and outbox insert in ONE statement (`inbound_events` CTE into `orchestrator_outbox`); a duplicate delivery is `200 duplicate`, a send or mark failure is `202 queued` (the outbox delivers it, so GitHub must not redeliver; the claim is never released). The web inserts the row in the same `withDb` transaction as the task or the decision, sends after commit, and marks sent in a second call; a failed send or mark shows the `queued` notice ("the sweeper retries within 15 minutes"). Previews have no queue: the row is inserted and nothing is sent. The sweeper's `outbox` part sends unsent rows older than 2 minutes that are due (by id, 200 per run), whatever the spend gate says (these inputs were already accepted; the consumer still honours `agents_paused`). A failed row counts an attempt, stores the error class, backs off `min(15 min * 2^attempts, 6 h)` and holds back the later rows of its group, in this run and in later ones while it backs off (FIFO). The consumer records a receipt (`orchestrator_receipts`) by logical key after it processed a keyed message (the relay's `delivery_id`, the web's `message_key`); a message whose key has a receipt is acknowledged as `duplicate` unprocessed, so a resend after SQS's 5-minute deduplication window or a send that was only not marked acts once. A crash before the receipt behaves as before (SQS redelivers the same message). Sweep and kcw-report messages have no key here (a report's receipt is written by its own transaction, next item). The key is also carried in the input and names its effect keys. The old resend buttons (console, inbox) are gone. AR4 adds orchestrator-written outbox rows: child start messages (key `task-<child>/start`, group `task-<child>`), inserted with the split or with the prerequisite's merge (`orch_rw` gains column INSERT on `message_key, group_id, body`, migration 0020). The sweeper's `outbox` part sends them, so a released child starts within one sweep interval (up to about 17 minutes). Duplicates are absorbed by the unique message key, the consumer receipt and `duplicate_start`.
- **Operation records (AR2 slice 2a, migration 0012):** `github_operations` holds one row per logical effect of a task: kind `plan`, `issue`, `dispatch` or `merge`, state `intent` or `done`, a request hash and the result. The effect key is `task-<id>/<kind>/<n>`, with `n` taken from `ops` in the checkpointed task data, which moves only when an operation finishes (a dispatch, an issue, a merge or a recorded refusal) or is abandoned and when the owner approves a replan. A step that fails keeps its previous checkpoint, so its re-run computes the same keys. The orchestrator writes the intent before the effect and the result after it (`orch_rw`: SELECT, INSERT, UPDATE of state and result only; the row never leaves the database, because the plan result holds private text). The same key with another request hash is a contradiction: nothing is sent, the key is abandoned and the owner gets a failure approval (approving restarts the operation under a new key).
  - *Planning:* the split result and then the title and issue text are recorded as returned; a re-run reuses them and does not call the model again (a deliberate replan after an owner approval is a new `plan` operation).
  - *Issue:* the body ends with a content-free marker `<!-- kcw-op: <key> -->`. An intent without a result is reconciled by listing the bot-created issues created since the intent (state all, newest first, the list endpoint, not search) and looking for the marker; found: reuse its number; not found: create. `tasks.github_issue` is stored as before.
  - *Dispatch (dev, QA and docs):* a re-run with a recorded run id reuses it. With an intent and no result it looks for the run by its exact run-name (`<role> task <id> op <n>`, created since the intent minus a 2-minute clock allowance as a bound only; `n` is the key's counter, so an earlier run of the task cannot match) and never dispatches again: found, the run is recorded and linked; not visible yet, the dispatch stays pending in the task data and each sweep looks again (the task keeps its phase; a decision cannot apply meanwhile); 10 minutes after the intent the task goes to the owner ("dispatch outcome is unknown"; approving dispatches under a new key). Any other change of phase abandons the pending dispatch. A dispatch GitHub refused with a 4xx other than 408 and 429 created no run: it is recorded as `done` with `dispatched:false`, the step fails as before and its retry uses the next key; 5xx, 408, 429, network errors and a missing status stay ambiguous.
  - *Merge:* an intent without a result reads the PR first: merged, the merge commit SHA is recorded and the step continues as a successful merge; otherwise it merges as before. A refused merge is recorded too, so the next merge of the task is a new operation.
  - *Checks* (`kcw/merge-rules`) have no records: a later check run of the same name on the same head supersedes the earlier one, which is what the ruleset reads, so a repeated post is harmless.
  - *Operation id on runs (AR2 slice 2b):* the dispatch passes `op` = `n` of the key (`task-<id>/dispatch/<n>`, decimal, the first dispatch is 0) to `agent-developer.yml`, `agent-qa.yml` and `agent-docs.yml` (`agent-scraper.yml` is not dispatched by the orchestrator and has none); their `run-name` is `<role> task <id> op <n>`. GitHub's run history is the durable record, so the workflows need no database access. *Admission:* trusted `prepare` lists the workflow's `workflow_dispatch` runs on `main` (newest 500) and admits itself only if it has the lowest run id among those with its exact run-name; otherwise it logs `run_not_admitted op=<n> first=<run id>` and outputs `skip=true`, which skips start, work, publish and report, so a duplicate or manual re-dispatch of the same operation does no paid work (a re-run of the same run keeps its run id and stays admitted). The per-task concurrency group serializes runs, so an earlier duplicate is visible to a later prepare. A missing or invalid `op` fails prepare; the validated `op` is part of the trusted context. *Fencing:* before any write, `publish` (also QA's review submission) checks again that it is still the first run of its run-name and that no run of the same workflow and task has a higher `op` (a newer operation supersedes it); otherwise it logs `publish_fenced reason=<not_admitted|superseded>`, writes nothing and succeeds. The run listing uses the job's own `actions: read` token, not the publisher App token. Reports of obsolete runs are fenced by the orchestrator (next item). A run that GitHub created but never made visible, or a dispatch that failed with an ambiguous error, still waits the 10 minutes and goes to the owner.
- **Reports and effect keys (AR2 slice 3, migration 0013):** each start and final report job sends ONE kcw-report message `{task_id, agent, run_id, run_attempt, job, op, event_type?, usage?}`. The identity comes only from trusted workflow context: `run_id` and `run_attempt` from the runner (`GITHUB_RUN_ID`, `GITHUB_RUN_ATTEMPT`), `job` (`start` or `end`) from the step, and `task_id`, `agent` and `op` from the validated prepare context (`op` null only for the scraper). The report key `report:<run id>:<attempt>:<job>` is the SQS MessageDeduplicationId and the consumer's receipt key. Each usage line carries `call: {job: work|review, index}`; its `usage_events.dedupe_key` is `report:<run id>:<attempt>:<call job>:<index>`, so identical lines of separate calls stay separate, a retry of the same report adds nothing, and a re-run (a new attempt) counts separately. The orchestrator writes the receipt, every usage line and the report's event in ONE transaction (`recordReport` in `agents/orchestrator/src/graph/`); a failure part-way writes nothing and the redelivery completes it once. The checkpointed task data lists the identities of the reports the thread applied (`applied_reports`, last 200); a report found there is a no-op. Usage is always recorded, also after the task ended; the event only when the agent is the one the phase waits on and its run is not obsolete. The task data keeps per role the op of its latest dispatch (`dispatch_ops`); a report with a lower op is logged `report_fenced` and has no lifecycle effect. Reports never change phase or status and never create approvals. Every other event and approval the machine writes carries an effect key `task-<id>/<input>/<event|approval>/<type or kind>/<n>` with `ON CONFLICT DO NOTHING` (`agent_events.effect_key`, `approvals.effect_key`), so a step re-run after a crash before its checkpoint repeats neither. `<input>` is the message's logical key when it has one, else the SQS message id.
- **Call records (AR3, migration 0019):** every in-process model call (the planner, the hub router, mood scoring, essay categorize and hooks) is recorded by the provider adapter (`@kcw/core/models`, option `onCall`, SQL in `models/ledger.ts`). Before each HTTP request (each retry attempt is its own request) a `usage_events` row with `dedupe_key = call:<uuid>` and outcome `started` and NULL tokens is written; after the response the same key is completed with the returned model and token counts (`reported`), or left with NULL tokens as `unknown` (sent, may be billed, no usage: network error, timeout, 5xx, invalid JSON, a response without usage) or `rejected` (a 4xx other than 408: not billed). The end write only replaces `started`, or `unknown` with a late `reported`; a duplicate writes nothing, and an end without its start inserts the row. A failed start write stops the call before it is sent; a failed end write fails the call and leaves the `started` row, which reads as unknown. The caller passes `call: {purpose, subject}` with the request (ids only). The planner's task id comes from its tracker (`trackPlannerCalls` in `agents/orchestrator/src/nodes/usage.ts`). Anthropic requests are retried by the adapter (the SDK client has `maxRetries: 0`; 408, 409, 429, 5xx and connection errors, two retries), so each attempt is recorded. Agent reports keep their identities (previous item) and carry purpose `work` or `review`. Readers: stored `cost_usd` wins; `rejected` costs $0; `started` or `unknown` without a stored cost is "usage unknown"; a model row without a price is "unpriced"; both count apart and add $0 to the cap total.
- **Stale events:** on resume the graph checks that the event matches `tasks.waiting_on` and `head_sha`. Stale or unexpected events are recorded and the thread re-interrupts unchanged.
- **Owner decisions:** the inbox enqueues `{type: "owner.decision", task_id, thread_id, message_key, resume: {approval_id, decision}}`. The graph applies it only if the thread waits on that approval and `approvals.status` already holds that decision; otherwise it is stale.
- **Sweep message** (P2-10 contract for P2-17): `{type: "sweep", task_id, thread_id}` per waiting or queued task. The graph decides itself whether a wait has timed out, retries a queued start (pause, in-flight limit) or an incomplete merge step, and runs inputs deferred while paused.
- **Sweeper** (EventBridge, every 15 min):
  - Tasks waiting longer than their limit (dev 60 min, ci 90, qa 60, owner never) get a `timeout` resume. The graph redispatches once, then fails the task to the inbox. AR6, reconcile before replacement: before the one redispatch of a timed-out Developer or QA wait, the orchestrator looks up the previous op's run (`findWorkflowRun`, exact run-name; the listing reaches back `DISPATCH_UNKNOWN_MINUTES` (10) plus the 2-minute clock slack before `waiting_since`, only as a bound). A run that is not `completed` is cancelled (`cancelRun`, idempotent, repeated on every sweep that still finds it running), `replacement_waits role=<role>` is logged and the step is `unchanged`; the reservation is kept. A run that is `completed` (any conclusion) or not visible: its attempt is marked `lost` when it has no end report, and the redispatch happens within the same reservation. The docs sweep is unchanged. Pause-all needs no extra code: reservations survive the pause and are reconciled by this rule after unpause. Residuals: the reservation is counted per task, not per run (a running run not visible in the listing at the timeout is replaced, so two runs can exist under one reservation); the listing reads one page; the advisory lock is not exercised under real concurrency in tests.
  - A docs task waiting on Docs-keeper (`dev`, §4.2 step 8) is judged by its `agent-docs.yml` run, found by run-name `docs task <id> op <n>` (the last dispatch's counter) among workflow_dispatch runs created since the dispatch (the dispatch API is not relied on for a run id): queued or running → wait, up to 150 min (job timeouts sum to 95), then the owner; succeeded after its start report with no PR → `done` silently; succeeded or skipped without a start report (agent workflows disabled) → `failed` with that reason and no inbox item; failed or timed out → the owner (approve re-dispatches Docs-keeper); cancelled (pause-all) or no run 30 min after the dispatch → redispatch once, then the owner.
  - Cancels running agent workflows when `agents_paused` is set.
  - Dispatches `preview-gc.yml` nightly (06:15-07:15 UTC, `dry_run=false`, unless already dispatched since 06:15).
  - Redelivers failed webhook deliveries of the orchestrator App (Q8 item 3): 3 h lookback, skipping guids that succeeded once, were refused with 4xx, are in `inbound_events` or had 4 attempts; at most 20 per run.
  - `releases` (`sweeper/releases.ts`, AR8a, migration 0023): (1) inserts a `task_releases` row for each `merged` event of the last 24 hours whose `detail.sha` is 40-hex (ON CONFLICT DO NOTHING; older merges and `by: external` merges create no row); (2) polls at most 20 rows with `verified_at IS NULL` merged within 7 days, never-checked and oldest-checked first, with one `deploy.yml` run list on `main` (per_page 50) per sweep. A run covers commit M when it is completed, was created at or after `merged_at` minus 10 minutes, and its head is M or a descendant (compare `ahead` or `identical`, at most 20 compare calls per sweep). The oldest covering `success` run wins (job success sets `verified_at`, the cache-clear step sets `deployed_at`, `failed_at` is cleared); otherwise the latest covering `failure` or `timed_out` run sets `failed_at`. `cancelled`, queued and in-progress runs are ignored. A verified row is final (the evidence update requires `verified_at IS NULL`); a failure keeps an earlier `deployed_at`. If the compare budget ran out before all candidate runs of a row were checked, no failure is recorded for it in that sweep. `checked_at` is stamped on every poll. With nothing to poll the part makes no GitHub call. It does not depend on the spend gate (read-only GitHub calls, runs while agents are paused), and a failure is reported by error class like the other parts. The deploy step `Record build id` prints `::notice title=kcw-build-id::<id>`; the sweeper keeps the id only if it matches `^[A-Za-z0-9_-]{1,64}$`, and a failing annotation read leaves `build_id` null with the job result unchanged. The owner console block "Releases" lists the last 10 rows with one label each (Merged, Deployed not verified, Verified, Deploy failed, No deploy result; the last is derived at read time when nothing is recorded 60 minutes after the merge); a failing read shows "Release state is unavailable right now." and leaves the rest of the console unaffected.
  - P2-17: own Lambda `kcw-prod-sweeper` (`@kcw/orchestrator/sweeper`, `infra/modules/scheduler`), Scheduler `cron(0/15 * * * ? *)` UTC passing `<aws.scheduler.scheduled-time>`; sweep dedupe id `sweep-<task>-<window>`. Reads `kcw/prod/orchestrator` (orch_rw + App key); may only SendMessage to `orchestrator-in`.
- **Pause-all** (`agents_paused`): no new dispatches, and in-flight agent runs are cancelled. Resumes queue up and are processed on unpause. `pipelines_paused` is a separate switch (Q2).

### 4.5 Public sanitization
There are two public surfaces: the office feed **and GitHub itself** (issues, PRs and CI logs are public).
1. The planner writes `public_title` from the task: product-level, no people, no personal facts, max 60 chars.
2. A deterministic check (`@kcw/core/sanitize`):
   - ASCII printable only, length <= 60;
   - rejects emails, phone numbers, URLs, digit runs > 4 and @handles;
   - rejects any token matching a contact name or alias (case-insensitive);
   - rejects a configurable blocklist.
3. On failure: the feed shows `Private task`, and GitHub issue text goes to an `issue_text` approval.
4. `is_private` defaults to true for every task, including capture-box `agent_request` entries (Q4) and console tasks (Q9). The owner can toggle it.
5. The feed endpoint `/api/public/agent-events?since=` uses the `web_public` role; CloudFront TTL is 5 s.
6. The task contract is public. Its `goal` and every `acceptance` item pass `checkText`; every `scope` and `context` path passes `checkText` with only the `url` code ignored (a file name such as `machine.ts` looks like a domain) and the contract path rule (letters, digits and `_ . / -`, no `..`, no leading `/`, no `//`, at most 200 characters). Any failure goes to the existing `issue_text` approval, whose reasons list the proposed title, body, acceptance and paths; approving publishes them as written. A plan whose body cannot form a valid contract (non-ASCII, size) goes to the owner as a planning failure instead. The worker renders the contract goal as markdown, so this sanitizer is the only guard on that text.
7. Workflows never print secrets or essay text, and `show_full_output` stays false. Extractor tests use public-domain fixtures only.
8. **Design target, not delivered (owner direction 2026-11-17, section 4.6):** delivered today, `@kcw/core/sanitize` guards public task titles (items 1-3) and contract text (item 6) by rejecting. The public log needs a replace mode of the same deterministic sanitizer for every published field: entry text, step results and state diffs. Known people (contact names and aliases) become bracketed filler names stable within one record (`[Person 1]`); emails, phone numbers, links and handles become `[email]`, `[phone]`, `[link]`, `[handle]`. Credentials, access links, raw tool payloads and raw provider messages are never published. Any error, or any field without a rule, keeps the whole record private (counted as withheld); a check never falls back to publishing unchanged. Names of people who are not contacts cannot be found deterministically, so (owner decision 2026-11-17, PH7) one bounded model call per record proposes spans: people's names (to `[Person n]`), specific places, workplaces and addresses (to `[place]`), and whether the record discusses another person's health, money, legal or relationship matters (then the whole record is withheld). The model only adds: the deterministic sanitizer applies the proposed replacements, then re-checks the final text with every rule; a model reply never marks text as safe, and a failed, timed-out, unparseable or over-budget call withholds the record. The call is recorded in the usage ledger like any bounded call. The owner's review screen on `/hub` shows the exact public text and lets the owner tap any word to replace it as well (it can only add replacements, never remove one); there is no per-record "keep private" control (owner decision).

### 4.6 Personal helper and the public log (owner direction 2026-11-17)

Status: accepted direction and design target. **Built: the record redactor and span-proposal call (PL1), the router step rows (PL2) and the owner review on `/hub` (PL3); publication and the public log page are not implemented**; current behaviour is in sections 3, 4.5 and 9 and in [HANDOFF.md](HANDOFF.md). Open points are in [OPEN-POINTS.md](OPEN-POINTS.md) ("Personal helper and the public log").

**Framing.** The product is the owner's personal helper; the public site shows it working with real inputs, real routing and real evidence. The autonomous development system (section 4.0) is how the site is built and maintained. Social was removed (owner 2026-11-17: the `/social` page, its daily job, the demo Following tab, migration 0024); playground ideas are held (visitor challenges, break-my-agent, public evaluation scoreboards). `/office` stays as the view of the development agents. The essays library and its spec are unchanged.

**Public log.** `/demo` stops being a synthetic hub and becomes the main public product: a cleaned log of the owner's entries, their routing, the trace of every step, the result, the checks, the corrections and the recovery. The public-domain Essays tab stays. The home page leads with the log. It starts on the day it ships: no backfill of older entries.

**Records extend `agent_events`.** Routing stays an ordinary application workflow with bounded model calls (section 4.0), not a LangGraph graph. Each step of an entry writes one `agent_events` row (built, PL2, migration 0025): agent `router`, `entry_id` set (and `task_id` null), `event_type` one of `ROUTER_STEPS` in `@kcw/core/events`, and a private `detail` of fixed codes and ids only (`apps/web/src/server/steps.ts`, never entry text, names or model replies). Steps: `captured` {source}; `routed` {kind, by model or owner, confidence and model, or the model's guess}; `needs_owner` {kind, confidence, model}; `route_failed` {code, attempt}; `derived` {kind, row_id, moved_from}; `contact_linked` {outcome linked, ambiguous, none or failed; note_id}; `mood_scored` {outcome scored, cap, failed or changed; diary_entry_id; model}; `calendar_suggested` {outcome; note_id; suggestion_id}; `corrected` {from, to}; and the owner's verdicts `confirmed` {kind}, `contact_chosen` {note_id, linked}, `calendar_added` and `calendar_dismissed` {suggestion_id} (PL3; written when the owner taps Correct, chooses a contact for a note, or adds or dismisses a suggestion). A recovery is a later success after a `route_failed`. A CHECK ties agent `router`, a non-null `entry_id` and the router types together; deleting an entry deletes its steps. Each step is written in the caller's transaction inside a savepoint: a failed step write is rolled back alone and logged by error class, never failing the capture or route, and a record with a missing step is treated as incomplete. Router rows are excluded from `v_public_agent_events` and from the office outbox trigger. The sanitized public copy is made at publication (PL4) from the stored rows and read through a new `web_public` view, on the pattern of `v_public_agent_events` and [office/LIVE-CONTRACT.md](office/LIVE-CONTRACT.md) (D10/D24 unchanged; new grants and views are owner-critical).

**Publication.** Automatic once the owner has reviewed the entry's route (owner decision 2026-11-17, PH4): "Correct" on `/hub` confirms it, a reassignment corrects it, and either publishes the record with no further approval step. The review is a verdict on correctness, not a privacy approval: sanitization alone decides what is safe, and a review cannot publish a withheld record. Entries wait for review indefinitely; the log shows how many await review, apart from the withheld count. Later steps (a calendar suggestion added or dismissed, a contact chosen) update the published record. Timestamps are rounded to the hour.

**Review on `/hub` (built, PL3, migration 0026, `apps/web/src/server/review.ts`).** After a route (model or Route again: routed or needs the owner) and after the owner's reassignment, the span proposal (`proposeSpans`) runs once per entry, bounded to 10 s and beside mood scoring, and its outcome is stored in `entry_public`; a stored `ok` proposal is never replaced. The region "Awaiting review (n)" lists, oldest first, every entry routed by the model, captured with a `captured` step (no backfill) and not yet reviewed. An entry counts as reviewed once it has a `confirmed` or `corrected` step, or a `routed` step by the owner. Each row shows the private text, the route, the exact public text (`createRecordRedactor` with every contact's name and aliases and the proposed and added terms, computed on each view; publication will snapshot it) or why it is withheld (the span outcome, `private-other`, or the redactor's failure code), "Correct" (writes `confirmed`; unlike other steps a failed write fails the action) and the "Change route" picker. Tapping a word of the public text offers Person or Place; the word must occur in the entry text as a whole word and is appended to `owner_people` or `owner_places` (never removed). A failed, capped, invalid or timed-out check offers "Find names again". Fail closed:
- Every route kind shows its sanitized text. Personal identifiers are replaced, not published: people by bracketed filler names, stable within one record (`[Person 1]`, `[Person 2]`), specific places, workplaces and addresses by `[place]`, emails, phone numbers, links and handles by `[email]`, `[phone]`, `[link]`, `[handle]`. A record about another person's health, money, legal or relationship matters is withheld.
- Never published: credentials or access links, raw tool payloads, raw provider error messages, raw model reasoning.
- If sanitization errors or cannot establish that a record is safe, the record stays private; only the count of withheld records is public. The log is labelled "Tasks published automatically after sanitization; some records withheld for privacy/security", with that count.
- The sanitizer is `@kcw/core/sanitize` in replace mode with the model-proposed spans and the owner's added replacements (section 4.5 item 8): models and the owner can only add replacements; the deterministic re-check decides.

**Corrections and recovery** (the resilience record, shown in detail). For a correction: the model's label, the owner's label and when. For a failed step: the step, its fixed error code (`provider_error`, `invalid_label`, `spend_cap`, `timeout`, ...), each attempt with its time and outcome, the recovery path (automatic retry, Route again, the owner's choice, Score again) and whether anything is still unresolved. These are sanitized step lines with fixed codes, not raw logs. "Routed, checks passed, no recovery needed" is a complete record.

**Evidence view (X-ray).** For a published entry a visitor opens its sanitized input and intended outcome, the actual steps and resulting changes, the checks that passed or failed, and the recovery, if any. `@kcw/xray` keeps describing only built components; the evidence view reads the public log, not the registry.

**Checks and evaluation** (owner decision 2026-11-17, PH4). A record shows three things:

1. **Checks:** deterministic pass/fail facts read back from stored state after each step. A check must be able to fail (on a bug, a provider misbehaviour or a timeout); properties the code already guarantees (a label in the allowed set, one transaction) are not shown as checks. No model call grades a record.
2. **Verdicts:** the owner's action on each step, or "not reviewed": the route confirmed ("Correct") or corrected (reassignment), a contact link chosen ("Choose a contact"), a calendar suggestion added (accepted) or dismissed (rejected).
3. **Check-list version:** the version of the check list below that the record was checked against, so changes over time are visible.

| Kind | Checks |
|---|---|
| all | derived rows match the kind (one, none for `agent_request`); each model call has a usage row (tokens, or marked usage-unknown); each bounded step finished within its bound; every failed step is followed by a success or an "unresolved" mark |
| `crm_note` | contact link outcome recorded, and a linked contact's name or alias appears in the note; calendar outcome recorded (`created`, `none`, `no-zone`, `invalid`, `failed`, `timeout`); a created suggestion's start is not before the capture time in the entry's time zone; a dummy-calendar event's id equals its suggestion's id |
| `diary` | all nine mood values present and in range, or "not scored" with a fixed reason |
| `todo`, `idea` | the derived body equals the entry text, or is marked "edited by owner" |
| `agent_request` | no derived row and no task created (revisit when agent requests get a destination) |

Correctness is not a per-record claim. Accuracy is a versioned aggregate per step over the owner's verdicts: route accuracy per router version (model and prompt), contact-link precision and calendar acceptance, each with its sample size. Planned capabilities are described as planned, and the log is never presented as a complete reliability record.

**Calendar.** The public log includes a Google Calendar of a separate dummy Google account (never the owner's), kept fresh from published entries: a published CRM note's calendar suggestion is added to the dummy calendar through the API with its sanitized title, and the log shows those events. Details are open (OPEN-POINTS PH8).

**Order of work.** AR9 first, then the social removal, then the public log in slices (OPEN-POINTS), then the remaining reliability work.
