## AR1: isolate candidate code from infrastructure authority

**Recommended approach:** use fresh, main-pinned privileged workflows and reviewed provisioning templates in the current account first. A second AWS account is an alternative if resource isolation cannot be demonstrated; do not add an account merely to avoid understanding the policy.

| Execution | May execute | Credentials/data |
|---|---|---|
| Candidate build/unit checks | PR source, dependencies, build scripts | Read-only repository access; no AWS role, id-token or management secrets |
| Trusted provisioner | Pinned trusted scripts, tool lock and Terraform templates; candidate build as validated data | Narrow preview role; Neon management key |
| Candidate migration/seed | PR migrations and seed against synthetic data | Disposable preview DB credential only; no AWS/Neon management access |
| Candidate browser checks | PR test code against the preview | Per-preview synthetic login only; no provisioning credentials |
| Trusted plan/report/cleanup | Trusted source and validated metadata | Narrow appropriate role; head/generation-bound reporting and teardown |

A build earlier in the same credentialed job is insufficient: candidate code can leave background processes behind. Splitting PR-controlled jobs alone is also insufficient while IAM accepts any `pull_request` OIDC subject. Remove that authority during cutover and trust a protected main-only provisioner/planner environment with an independently verified workflow source. Do not rely on a prompt or repository rule to enforce cloud permissions.

Implement AR1 in three reviewable slices:

1. **Authority and secret split.** Review `infra/bootstrap/iam.tf`, `secrets.tf`, `infra/preview/main.tf`, `infra/modules/web/*`, `infra/prod/main.tf` and preview GC. Prevent preview credentials from retagging/mutating production distributions or shared CloudFront policies/OACs. Prefer bootstrap-owned immutable shared preview policies/OACs over wildcard mutation. Separate the provisioner's Neon key from candidate runtime auth: preview Lambda currently reads all of `kcw/ci`, not just `e2e_login`. Give it only its preview's parameters/auth and resources. Give the production router a consumer-specific model secret. Verify preview DB credentials cannot access sibling/prod data. Do not read real secrets into the plan or logs.
2. **Trusted execution and artifact interface.** Replace privileged candidate execution in `.github/workflows/ci.yml` and relevant composites/GC paths. Bind repository ID, triggering workflow, run/attempt, PR head/base, artifact ID/digest and provisioning generation. Reject traversal, links, unexpected paths and excessive extraction sizes/counts. `scripts/lib/open-next-output.ts` checks layout, not hostile archive extraction. Privileged jobs run no candidate Terraform, providers, packages, config, hooks, migrations or tests, and restore no candidate caches. Reuse the established agent-publisher isolation patterns where applicable. Candidate migrations run only in their disposable DB runner so PR schema changes still get tested.
3. **Truthful plans and cutover.** Routine code plans use trusted infrastructure plus candidate build artifacts. If the candidate changes infrastructure/tooling, mark it as requiring an owner-reviewed plan for the exact head; a main-only plan must not pretend to evaluate changed infrastructure. Run that separately gated plan with reviewed tooling and bounded read-only authority. Generate plan summaries/merge inputs from trusted code. Bind aggregate checks and artifacts to the tested head and expected source; preserve required-check integrity when changing workflow topology. Serialize preview ownership or check generations so an older run cannot delete a replacement preview or approve a newer head.

**Cutover evidence:** inspect the actual OIDC/environment policies; revoke legacy PR-subject CI/plan trust and account for outstanding sessions before accepting candidate work. Verify create-with-tags still works, production retag/mutation is denied, legacy PR assumptions are denied, and legitimate preview cleanup succeeds. AWS create-with-tags may require dependent tagging authorization: one extra existing-tag condition is not proof of a working fix. Validate with policy analysis and a scoped disposable positive/negative run, without testing destructive calls against production. Rollback disables privileged automation and retains credential-free checks/trusted cleanup; it does not restore the broad legacy permissions.

## AR2: durable delivery and reconcilable effects

### Slice 1: database-to-SQS outbox

Change relay `src/relay.ts`, `store.ts`, orchestrator `sweeper/{store,sweep,deliveries}.ts`, web `server/{console,orchestrator-queue}.ts` and the relevant actions. Add a narrowly granted outbox in the next append-only migration after refreshed main: unique logical message key, normalized payload, pending/sent state and retry timestamps. Commit webhook receipt or owner/task mutation with its outbox intent; send after commit and drain unfinished rows through the existing sweeper. Reserve migration numbers after fetching current main.

Keep consumer receipts/effects keyed by the original logical message identity. A crash after SQS acceptance but before marking sent may resend beyond SQS's dedupe window; a new transport message ID is not a new logical event. Review `relay_rw`, `orch_rw` and `web_rw` grants independently.

**Tests:** crash after DB commit/before send; send succeeds but acknowledgement is lost; sent-state save fails; redelivery after the SQS dedupe window; concurrent drain; owner decision/task creation recovered after a failed send. No accepted work is lost and logical effects are deduplicated.

### Slice 2: GitHub intent and reconciliation

Change orchestrator `graph/{machine,store}.ts` and `github/{types,octokit,fake}.ts`. Freeze completed planning results and the selected sanitized issue request before external execution; replay consumes those saved results instead of replanning a different request under the same identity. Persist an operation intent before issue creation, workflow dispatch, check publication or merge: unique effect key, task/revision, request hash, sufficient request/result data, state and external reference. Keep private data private. Reconcile issues using a stable content-free marker, dispatches using an operation input/run identity, and merges using actual PR/head state. Trusted prepare/publish/report scripts and their gated workflows must carry and validate that identity.

An ambiguous timeout stays reconciling. A run missing from an immediately consistent-looking list does not justify blind redispatch. Trusted prepare must obtain one durable run admission per operation before entering the paid model job; publication fencing alone does not stop duplicate model spend. Reconcile failed/abandoned admissions and cancel/reconcile earlier execution before replacement. A timed-out lease is not proof that the old runner stopped. Fence obsolete attempts from publishing. This is recoverable logical processing, not a promise of external exactly-once execution.

**Tests:** remote success followed by socket error; database/checkpoint failure after remote success; delayed run visibility; contradictory requests under one operation ID; duplicate prepare runners; crash after admission but before model start; duplicate publishers and obsolete attempts. Existing valid work remains discoverable without duplicate issues or uncontrolled model runs.

### Slice 3: atomic reports and accounting identities

Change `packages/core/src/events`, `agents/report`, `scripts/lib/agent-pipeline.ts` and orchestrator report/store handling. Use stable report and call identities from run, attempt and job purpose, with distinct identities for genuinely separate calls. Reuse `usage_events.dedupe_key`; commit report receipt and all accounting lines atomically. Key event/approval effects too. Model name or array position alone is not a sufficient call identity.

**Tests:** partial multi-line report; retry under a new SQS ID; late usage after terminal state; a genuine rerun counted separately; duplicate event/approval suppression. Keep usage separate from lifecycle transitions.

## Validation and session handoff

Run focused existing tests for the touched interfaces, using fakes/PGlite. From the repository root, use `pnpm vitest run --project <name>` with the applicable projects: `@kcw/webhook-relay`, `@kcw/orchestrator`, `@kcw/report`, `@kcw/scripts`, `@kcw/core`, `@kcw/db`, or `web`. Then run the matching lint/typecheck/build checks from [INSTRUCTIONS](agents/INSTRUCTIONS.md); CI remains the publication gate. Workflow changes also need `actionlint`; infrastructure changes need formatting/validation and scoped plan review. Never run a production migration merely to test the migration runner.

For docs-only preparation, `node scripts/check-agent-docs.mjs` and `git diff --check` are sufficient. Existing source-policy string tests do not establish deployed IAM behavior. Positive/negative cloud calls, real webhook retry, dispatch reconciliation, QA federation, cancellation, grants, notification and restore checks each need scoped runtime evidence.

Before passing the session, record exact local branch/commit, dirty files, fetched and stale refs, checks actually run, current source versus deployed observations, the next slice, unresolved policy choices and the source/scope of authorization in HANDOFF plus the local overlay. The execution session must refresh source and verify access; this document transfers context, not credentials or missing live approval.
