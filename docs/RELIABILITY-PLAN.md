## Start and authorization

1. Follow [CONTINUITY](agents/CONTINUITY.md): attempt a current fetch and inventory branches, worktrees and dirty changes. Preserve other sessions' work. If terminal networking fails, pin the connected GitHub ref and verify source through that interface while labeling local refs stale; do not report a successful Git fetch. Reconcile the local direction commit and this plan with main before implementation; use owned task branches/worktrees.
2. Implement one reviewed slice at a time. Include matching behavioral docs and evidence in each PR. Keep existing LangGraph/Lambda/SQS/Postgres/Actions infrastructure and approved worker profiles; add no general orchestration platform.
3. The owner approved the direction and requested preparation for execution/CI in a connected session. The slices below are proposed implementations, not approval to apply IAM, change secrets/protection, deploy migrations/grants, enable workers, or run paid acceptance. Preserve the exact-step gates in [HANDOFF](HANDOFF.md). Plan and review privileged changes before requesting their scoped live approval.

## AR1: isolate candidate code from infrastructure authority

Status (2026-11-16): AR1 is complete and live. Slices 1 to 3 are merged (#106-#109), the owner applied the bootstrap changes on 2026-11-14, and the trusted `prod-plan` job has verified every PR since #110. The text below keeps the wording of the implementation plan. Open decision: whether `kcw-gh-plan` keeps its `pull_request` trust, which now serves only the advisory `ci.yml` plan, before agents are enabled.

**Recommended approach:** use fresh, main-pinned privileged workflows and reviewed provisioning templates in the current account first. A second AWS account is an alternative if resource isolation cannot be demonstrated; do not add an account merely to avoid understanding the policy.

| Execution | May execute | Credentials/data |
|---|---|---|
| Candidate build/unit checks | PR source, dependencies, build scripts | Read-only repository access; no AWS role, id-token or management secrets |
| Trusted provisioner | Pinned trusted scripts, tool lock and Terraform templates; candidate build as validated data | Narrow preview role; Neon management key |
| Candidate migration/seed | PR migrations and seed against synthetic data | Disposable preview DB credential only; no AWS/Neon management access |
| Candidate browser checks | PR test code against the preview | Per-preview synthetic login only; no provisioning credentials |
| Trusted plan/report/cleanup | Trusted source and validated metadata | Narrow appropriate role; head/generation-bound reporting and teardown |

A build earlier in the same credentialed job is insufficient: candidate code can leave background processes behind. Splitting PR-controlled jobs alone is also insufficient while IAM accepts any `pull_request` OIDC subject. Remove that authority during cutover and trust a protected main-only provisioner/planner environment with an independently verified workflow source. Do not rely on a prompt or repository rule to enforce cloud permissions.

Implement AR1 in three reviewable slices:

1. **Authority and secret split.** Review `infra/bootstrap/iam.tf`, `secrets.tf`, `infra/preview/main.tf`, `infra/modules/web/*`, `infra/prod/main.tf` and preview GC. Prevent preview credentials from retagging/mutating production distributions or shared CloudFront policies/OACs. Prefer bootstrap-owned immutable shared preview policies/OACs over wildcard mutation. Separate the provisioner's Neon key from candidate runtime auth: preview Lambda currently reads all of `kcw/ci`, not just `e2e_login`. Give it only its preview's parameters/auth and resources. Give the production router a consumer-specific model secret. Verify preview DB credentials cannot access sibling/prod data. Do not read real secrets into the plan or logs.
2. **Trusted execution and artifact interface.** Status: PR A (#107: `.github/workflows/preview-trusted.yml` plus the credential-free `candidate-build` job; no dependency cache is shared with default-branch jobs: only `checks` and `candidate-build` use the pnpm cache) is merged. PR B (cutover) is merged (#108) and live: the old `preview` job and the shadow offset are gone, the PR-closed GC moved to `pull_request_target` in environment `preview-gc`, and `kcw-gh-ci` trusts only `environment:preview-gc` (`kcw-gh-plan` keeps `pull_request`: read-only plan, owner decision; candidate-infra plans stay automatic, D25 residual accepted). It takes effect after the owner-approved bootstrap apply ([runbook](runbooks/bootstrap.md#ar1-slice-2-cutover)). The two items deferred here are done in slice 3. Replace privileged candidate execution in `.github/workflows/ci.yml` and relevant composites/GC paths. Bind repository ID, triggering workflow, run/attempt, PR head/base, artifact ID/digest and provisioning generation. Reject traversal, links, unexpected paths and excessive extraction sizes/counts. `scripts/lib/open-next-output.ts` checks layout, not hostile archive extraction. Privileged jobs run no candidate Terraform, providers, packages, config, hooks, migrations or tests, and restore no candidate caches. Reuse the established agent-publisher isolation patterns where applicable. Candidate migrations run only in their disposable DB runner so PR schema changes still get tested.
3. **Truthful plans and cutover.** Status: merged (#109) and live since the owner's bootstrap apply and the `prod-plan` environment ([runbook](runbooks/bootstrap.md#ar1-slice-3-trusted-merge-rules-input)). The trusted `prod-plan` job of `preview-trusted.yml` plans main's infrastructure with the verified `candidate-prod` build; `merge-rules-input` (format 2) comes only from it and lists the PR's own `infra/` and `.github/` paths as `uncoveredPaths`, each sent to the owner; the orchestrator reads it only from the run the shared trusted-run check accepts; `ci.yml`'s plan is advisory. Remaining: the live cutover evidence below. Original scope: Routine code plans use trusted infrastructure plus candidate build artifacts. If the candidate changes infrastructure/tooling, mark it as requiring an owner-reviewed plan for the exact head; a main-only plan must not pretend to evaluate changed infrastructure. Run that separately gated plan with reviewed tooling and bounded read-only authority. Generate plan summaries/merge inputs from trusted code. Bind aggregate checks and artifacts to the tested head and expected source; preserve required-check integrity when changing workflow topology. Serialize preview ownership or check generations so an older run cannot delete a replacement preview or approve a newer head.

**Cutover evidence:** inspect the actual OIDC/environment policies; revoke legacy PR-subject CI/plan trust and account for outstanding sessions before accepting candidate work. Verify create-with-tags still works, production retag/mutation is denied, legacy PR assumptions are denied, and legitimate preview cleanup succeeds. AWS create-with-tags may require dependent tagging authorization: one extra existing-tag condition is not proof of a working fix. Validate with policy analysis and a scoped disposable positive/negative run, without testing destructive calls against production. Rollback disables privileged automation and retains credential-free checks/trusted cleanup; it does not restore the broad legacy permissions.

## AR2: durable delivery and reconcilable effects

Sweeper part `outbox` (every run, not spend-gated; backoff `min(15 min * 2^attempts, 6 h)`, per-group FIFO hold). Consumer receipts by logical key. Details in DESIGN section 4.3. Remaining: live acceptance after the migration is applied.

Change relay `src/relay.ts`, `store.ts`, orchestrator `sweeper/{store,sweep,deliveries}.ts`, web `server/{console,orchestrator-queue}.ts` and the relevant actions. Keep consumer receipts/effects keyed by the original logical message identity. A crash after SQS acceptance but before marking sent may resend beyond SQS's dedupe window; a new transport message ID is not a new logical event. Review `relay_rw`, `orch_rw` and `web_rw` grants independently.

### Slice 2: GitHub intent and reconciliation

Status: 2a (orchestrator side) merged in #112; 2b (workflow side) merged in #113. 2a: migration `0012_github_operations` (gated: the deploy applies it after merge), operation records for the planner result, the issue, agent dispatches and the merge, reconciliation on replay and the owner path for a dispatch whose run never appears (DESIGN sections 4.2 and 4.3). Report-side fencing of obsolete runs goes with slice 3 report identities.

Change orchestrator `graph/{machine,store}.ts` and `github/{types,octokit,fake}.ts`. Freeze completed planning results and the selected sanitized issue request before external execution; replay consumes those saved results instead of replanning a different request under the same identity. Persist an operation intent before issue creation, workflow dispatch, check publication or merge: unique effect key, task/revision, request hash, sufficient request/result data, state and external reference. Keep private data private. Reconcile issues using a stable content-free marker, dispatches using an operation input/run identity, and merges using actual PR/head state. Trusted prepare/publish/report scripts and their gated workflows must carry and validate that identity.

Reconcile failed/abandoned admissions and cancel/reconcile earlier execution before replacement. A timed-out lease is not proof that the old runner stopped. Fence obsolete attempts from publishing. This is recoverable logical processing, not a promise of external exactly-once execution.

## Validation and session handoff

Run focused existing tests for the touched interfaces, using fakes/PGlite. From the repository root, use `pnpm vitest run --project <name>` with the applicable projects: `@kcw/webhook-relay`, `@kcw/orchestrator`, `@kcw/report`, `@kcw/scripts`, `@kcw/core`, `@kcw/db`, or `web`. Then run the matching lint/typecheck/build checks from [INSTRUCTIONS](agents/INSTRUCTIONS.md); CI remains the publication gate. Workflow changes also need `actionlint`; infrastructure changes need formatting/validation and scoped plan review. Never run a production migration merely to test the migration runner.

For docs-only preparation, `node scripts/check-agent-docs.mjs` and `git diff --check` are sufficient. Existing source-policy string tests do not establish deployed IAM behavior. Positive/negative cloud calls, real webhook retry, dispatch reconciliation, QA federation, cancellation, grants, notification and restore checks each need scoped runtime evidence.

Before passing the session, record exact local branch/commit, dirty files, fetched and stale refs, checks actually run, current source versus deployed observations, the next slice, unresolved policy choices and the source/scope of authorization in HANDOFF plus the local overlay. The execution session must refresh source and verify access; this document transfers context, not credentials or missing live approval.
