## Decisions and security holds

**Q12 — planner defaults, owner confirmation pending.** [DESIGN §11](DESIGN.md#11-spec-conflicts-and-open-questions) records: top-level tasks split into 1–5 subtasks, never recursively; one subtask runs the parent PR loop without a child row. With 2+ subtasks, each gets a child task, copied source/privacy, private subtask text, its own thread/title/PR branch. Parents with children occupy no in-flight slot; they wait with `waiting_on` null until a sweep marks all-merged as `done`, or any failed/cancelled child as `failed` (up to one sweep lag). Model output is validated without a schema dependency, retried once on invalid output, then escalated as `critical_pr` (approve replans, reject fails); provider failures redeliver through SQS.

**Q13 — usage defaults, owner confirmation pending.** Although baseline DESIGN lists it among resolved material, the current handoff explicitly leaves confirmation pending. Stored `cost_usd` wins; otherwise use provider/model price effective on the event's UTC day, otherwise display “no price,” never $0. Writers currently leave model cost null, so later prices apply retroactively. Relay records each allowlisted completed workflow run attempt, with or without a task, as elapsed wall-clock minutes (`run_started_at` → `updated_at`, not GitHub billable job minutes), cost 0, deduped by key. Agent workflow filename maps to developer/qa/scraper/docs; other workflows map to orchestrator. Agent reports must omit `--minutes` to avoid double counting. Ranges are UTC, default 30 days, maximum 366.

**Q14 — proposed workflow behavior, not approved.** Full detail is in [#29's DESIGN at the observed head](https://github.com/kentkodes/kentcrosswise/blob/b7cfd95c67213635db4c21904d2df1ba283ae095/docs/DESIGN.md#11-spec-conflicts-and-open-questions). Developer/Scraper inputs are `{task_id, issue, mode=implement|fix, pr}`; QA/Docs use `{task_id, pr}` (Docs means merged PR, skipping Docs App merges). Runs are on `main`, serialized by task, and validate repository/task-branch/PR state. The proposed deviation from §4.1 is a read-only workflow token for Claude: it commits, then an App-token publisher copies validated descendants into a fresh hook/config-free repository and pushes without force to `kcw/task-<id>`. QA publishes tests only and a structured decision on the resulting head; Docs publishes only its allowed docs. All agents reject `.github/**` and `.claude/**`. Proposed allowlists drop direct `git push`/`git switch` and add file tools; current merged playbook lists are adapter documentation, not proof those workflows are live. AWS credentials remain step outputs and the App key is dropped from job env after token creation. QA uses trusted `main` at root and sparse PR data under `pr-head/`. Reports include action execution-file model usage, omit minutes (Q13), and repeat the start event on success because reports require an event; usage-only reports are a follow-up proposal. Queue URL uses account variable plus fixed FIFO name; fix context uses failed check runs/latest QA request, not logs (`actions: read` absent). Action inputs were tag-checked; plugins remain empty.

**Q15 — confirmed shared-runner security blocker; proposed fix requires owner decision.** PR/issue-controlled code and later App-token publishing/review share a runner user. `$GITHUB_ENV`/`NODE_OPTIONS` can influence later steps; a read-only token in the model step does not isolate publishing. The broader risk is confirmed: the job has `id-token: write`, `kcw-gh-agent` trusts jobs on `ref:refs/heads/main`, and its policy can read all four `kcw/github/*-app` keys; compromise can reach a QA approval identity.
