## Ownership and changes

- Public pages: `/` (Paper home), `/demo` (simulated hub in an app frame; tabs Today, People, Mood, Following, Notes and Essays), `/office`, `/bot`, `/terms` and `/privacy`. A header toggle turns on the X-ray overlay. `/terms` (15 November 2026) and `/privacy` (17 November 2026) state only what the code does; `/privacy` names the third-party services in use (model services, web push, Google Calendar and read-only YouTube, Instagram; TikTok is not connected) and states the Google API Services User Data Policy Limited Use requirements, so update it and its "Last updated" date when an integration ships or tracking is added.
- Owner pages (Google sign-in, allowlisted owner). The owner nav is one row of six primary links, Hub, Inbox, Todos, Diary, Ideas and Contacts, plus a native "More" disclosure holding the other eight in this order: Mood, Social, Projects, Essays, Boss console, Usage, Connections, Notifications. The disclosure opens without JavaScript and its panel overlays the content; the summary reads "More" or "More: <section>" when the current page is hidden there, and every link and the summary has a 44px tap target. Sub-pages keep their section marked; detail and setup pages are reached by URL.
- Subtask ordering (AR4): the planner marks each subtask as waiting for the previous one (default) or independent; a child starts from an outbox message the sweeper sends once its prerequisites have merged (within one sweep interval). Each merged task records its merge commit (`tasks.merge_sha`) and the consumer's issue footer lists its prerequisites' merge commits. A failed or cancelled child that blocks others parks the parent for the owner.
- Owner console: one capacity line (active workers, admitted work with parked owner, CI and waiting-for-a-worker counts, queued) and a "Releases" block of the last 10 merge commits (Merged, Deployed not verified, Verified, Deploy failed, No deploy result). `claimExecution` (AR6) writes `tasks.execution_wait` when it refuses a reservation.
- Task contract (AR5a): the planner reads the `## Layout` brief at the `main` head, the public-title node returns acceptance, scope and context, and the sanitized contract is built after the issue is published and sent as the `contract` input of every Developer and QA dispatch. The worker validates it, binds its hash in the context, bounds `task.md` at 49,152 bytes and puts the hash in its reports. QA of a Docs-keeper PR takes no contract (decided by the PR author id). A work task planned before contracts existed fails at its dispatch; a missing brief or prerequisite merge commit goes to the owner.
- Revisions, attempts and replan (AR5b, migration 0021, tables `task_revisions`, `task_attempts`, `task_evidence`, `orch_rw` only): each dispatch is an attempt row; QA approvals and changes requests count only for the current revision, head and a started latest QA attempt, and the merge step re-checks CI and QA evidence. Approving a failure after the Developer used all attempts replans the task (new contract revision, the PR kept, CI reused for an unchanged head, QA again); a task planned before contracts keeps the old retry and its dispatch fails it.
- Execution reservations (AR6, no migration): `claimExecution` reserves a Developer or QA run before its dispatch; `ACTIVE_EXECUTION_LIMIT` is 1 (owner decision: one worker run at a time for AR9, raised once cost and live behaviour are confirmed) under `IN_FLIGHT_LIMIT` 4. A refused dispatch is retried by the next sweep (a first dispatch still `planning`: the 15-minute stale-planning sweep). A timeout cancels and reconciles the previous run before replacing it.
- Release state (AR8a): the sweeper part `releases` records merged, deployed and verified per merge commit in `task_releases` from `deploy.yml` runs (a verified row is final; the deploy step `Record build id` supplies the build id). Merges before 0023, by the owner scripts or external are not tracked.
- Capture and derived records: a routed capture creates one derived row (CRM note, diary entry, todo or idea) in the route transaction (`applyRoute` in `apps/web/src/server/derived.ts`). Reassignment moves the current body; a same-kind save is a no-op.
- Contact linking: a routed CRM note is matched to a contact by name inside the route transaction (`applyRouteLinked` in `router.ts`, `linkCrmNote` in `contacts.ts`). One match links it; several show "Choose a contact" and a `contact_match` item on `/inbox`; none leaves it unlinked. A failed link keeps the route.
- Mood scoring: a diary row created by a route is scored after the transaction commits, bounded to 6 s (`scoreCreated`). A timeout or failure leaves "Not scored" with "Score again" on the diary page. Without `KCW_MODELS_SECRET` the page says "Mood scoring is not set up here".
- Calendar: after a route creates a CRM note, one bounded model call may suggest a dated plan (`suggestFromNote` in `calendar.ts`, 6 s bound; also after owner reassignment). The `/inbox` calendar region offers one-tap add to Google Calendar or dismiss.
- Google: `/connections` connects Calendar events and read-only YouTube with a refresh token in `kcw/prod/google-owner-token`, and disconnects (revoke at Google).
- Social: `/social` has manual entries, and its add form marks an account for the daily job ("Numbers from": Manual entry or Daily job (API); ingest `api` is allowed for one YouTube and one Instagram account, never TikTok, and cannot be changed on an existing account). The `social-daily` job writes one daily YouTube and Instagram snapshot per UTC day for the accounts with ingest `api`. The owner has not added one yet (owner step 2 in OPEN-POINTS), so the job has read nothing so far.
- Web push: the `inbox-push` job runs every 15 minutes and sends one generic notification to each subscribed device when open inbox items have not been announced. It returns `off` until the VAPID keys exist. `/notifications` enables, disables and tests a device.
- Scheduled web jobs: EventBridge Scheduler invokes the server function with `kcw_job`; the origin wrapper routes it to the fixed registry (`social-daily` at 06:15 UTC, `inbox-push` every 15 minutes).
- Release: `deploy.yml` builds before the production migration, and two `if: failure()` steps publish to the alerts topic. Failure alarms publish to `kcw-prod-alerts` (SNS, no subscriber yet; [alerts runbook](runbooks/alerts.md)).
- Agents: planner on Claude Opus 5.5 at high effort; Developer, Scraper-builder and Docs-keeper on DeepSeek Flash; QA on Claude Haiku 5.5 through Anthropic workload identity federation.
- Accounting (AR3): every in-process model call (planner, hub router, mood, calendar suggestion, essay categorize and hooks) writes call records to `usage_events`: `started` before the request, then `reported`, `unknown` (sent, no usage: tokens NULL) or `rejected` (4xx: $0). `/console/usage` shows unpriced and usage-unknown counts next to every total. The monthly $50 control stays soft: those rows add $0 to the cap total.
- Essays: 300 approved seeds; 8 full Gutenberg texts in the private bucket; the rest are link-only rows. All 8 stored essays have a hook (`essays.hook`). Validator v2 (E7): `essays.text_hash` is the sha256 of the normalized text, and the store phase quarantines near duplicates.
